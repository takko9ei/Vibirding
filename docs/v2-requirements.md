# Vibirding v2 · 需求与决策文档

> 本文件记录 v2 改造的**需求、已拍板的决定、待决项、以及分步开发规划**。
> 与 `docs/SNAPSHOT-v1.md`（v1 真实现状快照）配套使用：快照说"现在是什么"，本文说"要变成什么"。
> 延续 v1 的开发纪律：**先文档后代码、一次一个模块、切片式推进、每切片可独立验收**。

---

## 0. v1 现状（起点）

v1 已完成 S1–S8 并打 tag：单条自然语言笔记 → 一条结构化 Observation，
含手写 agent harness（工具循环 / 权限闸 / 预算 / 容错 / trace）、三个外部工具
（read_log / range_check(eBird) / bird_id(懂鸟)）、append-only JSONL 存储、CLI 入口、
eval 测试集（离线 13/13 = 100%，在线 11/13 = 84.6%）。

**v1 已知边界（S7 报告）**：
- 用户指定种名时不必然触发季节核验（模型行为不稳定）；
- 模糊量词（"十几只"）不给估值，倾向置空。

---

## 1. v2 总体定位变化

**从**：单条笔记 → 一条记录，CLI 交互，JSONL 存储
**到**：一整篇多物种笔记 + 一批照片 → 拆解、鉴种、图文匹配 → **多条**记录 → PostgreSQL，Web 界面交互

**核心理念**：符合人类真实记录习惯——用一个记事本记一天，而不是每看一只鸟开一条记录。
**产品定位**：观察记录本 + 媒体库。

---

## 2. 需求一：批量处理 + 图文匹配

### 2.1 输入形态
一段自然语言（含多条观测）+ 任意数量照片。
示例：`"我今天在井之头公园看到了3只灰喜鹊，一群十只左右的北长尾山雀，两只鸬鹚"` + N 张照片

### 2.2 处理流程（四阶段）

1. **文本拆分**：整段拆成多条独立观测（上例 → 3 条）。
   共享上下文（地点"井之头公园"、日期"今天"）**下发到每一条**。
2. **照片鉴种**：每张照片过懂鸟 API，得候选种 + 置信度。
3. **图文匹配**：照片鉴定结果与文本记录配对。
   - 匹配上 → 照片归属该记录，合并为一条完整观测（有文字有图）；
   - 匹配不上（照片物种未出现在任何描述中）→ **自动新建一条观测记录**。
4. **写入**：所有记录（合并的 + 新建的）经用户确认后写入数据库。

### 2.3 已拍板的规则

| 决定项 | 结论 |
|---|---|
| 同种多张照片 | **全部归到同一条记录** |
| 一张照片多只鸟 | **以懂鸟返回的第一候选为准** |
| 数量冲突（描述3只 vs 照片2张） | **以描述为准**，照片仅作证据 |
| 权限确认粒度 | **预览全部 → 一次确认**（不逐条问） |
| 部分失败 | **成功的落盘，失败的提示用户**（API 层需支持部分成功） |
| 照片命名 | **按内容哈希重命名**（天然去重、避免重名） |

### 2.4 ⚠️ 待拍板：物种名规范化（重要，影响数据库设计）

**问题**：v1 的 `Observation.species` 是自由字符串，无名录约束。用户写"乌鸦"时，模型是否规范成"大嘴乌鸦"**靠模型自觉、非系统保证**。而懂鸟返回正式种名。**因此严格字符串匹配当前不可靠。**

两条路：
- **轻**：prompt 强制"species 必须写正式中文种名" + 匹配时做基本归一化（去空格等）。工作量小，仍靠模型自觉。
- **重（推荐）**：引入物种名录（eBird taxonomy 有中文 locale / 懂鸟有物种 ID），描述与照片结果**都映射到同一物种 ID**，用 ID 匹配。可靠，且物种 ID 是数据库天然主键素材（支撑"我见过多少种""按种筛照片"）。需增加 `species` 表。

**待你拍板。** 未定之前，图文匹配的可靠性无法保证。

## 3. 需求二：PostgreSQL 替换 JSONL

### 3.1 要做的
把 `memory/log.py` 的 append-only JSONL 换成 PostgreSQL。
**`append_log` / `read_log` 两个工具的对外契约不变**，只换底层实现
（复用 v1 "provider 中立"的同一思路：换实现不换契约）。

### 3.2 已拍板

| 决定项 | 结论 |
|---|---|
| 部署 | **Docker 本地起 PostgreSQL** |
| 照片存储 | **文件系统持久化 + 数据库存路径/元数据**（不把二进制塞进 DB）；建 `media/` 目录，哈希命名 |
| 旧数据迁移 | **不需要**（现有 JSONL 均为编造的测试数据） |
| 数据访问方式 | **ORM（SQLAlchemy）**——与现有 pydantic 模型对应顺畅，且是 FastAPI 标准组合 |
| `flags` 列表字段 | **JSONB 列**——简单、灵活、PG 查询能力足够 |
| 用户系统 | **预留 user_id，暂不实现** |

### 3.3 表设计（初步）
- `observations`：对应现有 Observation schema（id / timestamp / place / obs_date / species /
  count / behavior / raw_note / confidence / source / flags(JSONB) / user_id(预留)）
- `photos`：哈希文件名 / 原始文件名 / 鉴定结果 / 置信度 / **外键关联 observation**（一对多）
- `notes`（或 sessions）：记录"这一批是同一次提交"，便于回溯一篇笔记拆出了哪些记录
- `species`（**仅当物种规范化走"重"方案时需要**）

## 4. 需求三：Web 前端

### 4.1 已拍板

| 决定项 | 结论 |
|---|---|
| 技术栈 | **FastAPI（后端）+ React（前端）** |
| 写入流程 | **预览 → 用户确认 → 才写库**（v1 权限闸在 Web 上的落地形态） |
| 页面数 | **两个**：输入页 + 记录浏览/管理页 |
| 跨提交上下文 | **暂不做**（每次提交独立成一轮）；"修改刚才那条"走管理页编辑，比让 agent 猜更可靠 |

### 4.2 页面 A：输入页
类主流 AI 聊天界面：文本框 + "插入图片"按钮 + "发送"按钮。

两种用法，**由 agent/意图判断决定**（延续 v1 CLI 不做子命令的决定）：
- 发一堆描述 + 一堆图片 → 默认行为：整理成结构化记录（走预览确认流程）
- 问"请列出最近的 10 条我的观察数据" → 查询并展示

> **重要设计判断**：查询类请求**不必过 LLM**。"列出最近10条"就是 `GET /api/observations?limit=10`。
> 聊天界面不代表所有操作都要经过大模型——让 agent 查库再复述既慢又可能出错。

### 4.3 页面 B：记录浏览/管理页
浏览、筛选、编辑、删除观测记录；查看关联照片（媒体库形态）。

## 5. API 设计

### 5.1 设计原则
**API 是"能力的暴露"，不是"页面的拼装"。** 按资源/能力设计，前端自由组合；
这样换界面、加移动端时 API 不用重写。

### 5.2 三个关键考量

1. **预览与写入必须拆成两步**（副作用分离）
   只读的解析可随意重试；有副作用的写入单独隔离。
   **这是 v1 权限闸在 Web 上的自然延续，值得写进 DECISIONS。**
2. **上传独立成一步**
   照片不与文本混在同一请求反复传（改文本重新解析时无需重传图）。
3. **长耗时操作预留异步**
   parse 要跑 LLM 拆分 + N 张照片过懂鸟（上传+轮询）+ eBird 核验，**可能数十秒**。
   **决定：先做同步**（前端转圈等），但返回结构预留 job 语义，将来可改异步轮询。

### 5.3 初步接口清单

```
# 媒体
POST   /api/media                上传照片 → {media_id, hash, url}

# 解析（只读、无副作用、可重试）
POST   /api/parse                {text, media_ids[]}
                                 → {draft_observations[], unmatched_photos[], warnings[]}

# 观测记录
POST   /api/observations         批量写入用户确认后的记录 → {created[], failed[]}
GET    /api/observations         列表，支持 ?limit=10&place=&species=&date_from=
GET    /api/observations/{id}    单条详情
PATCH  /api/observations/{id}    编辑（管理页用）
DELETE /api/observations/{id}    删除

# 物种（仅"重"方案需要）
GET    /api/species?q=乌鸦        物种名查询/联想
```

**设计要点**：
- `/api/parse` 返回含 `unmatched_photos`——即"照片物种未出现在描述中"那批，前端单独展示、由用户决定是否建新记录。
- `POST /api/observations` 返回 `created` 和 `failed` 两个列表——对应"部分成功"策略，API 层面就要支持，不能只返回一个布尔。

## 6. 分步开发规划

**依赖关系：数据库 → 批量匹配 → 前端。三件事不要并行。**

### 第 0 步：准备
v1 打 tag（已完成）；开 `v2` 分支；把 SNAPSHOT-v1.md 与本文件存入仓库。

### 第 1 步：接 PostgreSQL（最独立、风险最低）
只换存储底层，`append_log`/`read_log` 契约不变。
**验收：用 v1 现有 eval 验证没退化（离线仍应 13/13）。**
理由：不引入任何新逻辑，出问题好定位；地基先换稳。

### 第 2 步：批量拆分 + 图文匹配（核心难点）
拆成六小步，每步可独立验收：
1. 文本拆多条 Observation（共享上下文下发）
2. 图片批量过懂鸟的预处理（纯脚本，不涉及 agent，最好测）
3. 匹配逻辑——**先 dry-run，只输出配对方案不写库**（匹配最易错，先只说不做）
4. 真写入 + 批量确认（权限闸批量形态）
5. 未匹配照片 → 建新记录
6. 扩展 eval：覆盖多记录拆分正确性、匹配正确率；确认 v1 单条用例未退化

### 第 3 步：前端
1. FastAPI 暴露 API（先用 curl/HTTP 客户端测通，不碰界面）
2. React 输入页（文本框 + 插图 + 发送 + 预览确认）
3. React 管理页（浏览/筛选/编辑/删除 + 媒体展示）

### 第 4 步：收尾
更新 STATUS / DECISIONS / README，打 `v2.0` tag。

## 7. 待拍板清单（开工前需定）

1. **物种名规范化走"轻"还是"重"**（见 §2.4）——推荐"重"，但增加工作量。**这是最重要的一个。**
2. 照片自动重命名为种名（v2 早期讨论提过，本轮未提）——**还要不要？**
   接了数据库+哈希命名后，重命名的意义已变（媒体库靠 DB 关联而非文件名）。倾向不做。
3. `notes/sessions` 表要不要做（记录"同一次提交"的批次关系）——影响回溯能力。

---

## 8. 延续 v1 的开发纪律（不变）

- `docs/architecture.md` 仍是唯一事实来源；v2 要**先改文档再写代码**。
- 一次只实现一个模块，review 后再继续；每个能跑的切片 commit 一次。
- 每个切片配离线自检；核心改动后跑 eval 确认无退化。
- 边做边往 DECISIONS.md 记取舍（三行体）。
- 不引入不必要的框架/抽象；能用工具解决的不上子 agent。
